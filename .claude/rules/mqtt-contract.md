# MQTT Contract

The single source of truth for what moves between the ESP32, the FastAPI
service on the Pi, and the Flutter app. Three codebases in three languages
encode this contract; if it is not written down in one place they drift
silently and the app shows a state the gate is not in.

**Changing anything here means changing the firmware, the server, the app, and
this file in the same change. No exceptions.**

## Broker

- Mosquitto on the Pi 5, bound to the LAN interface only. The broker is never
  routed through the Cloudflare Tunnel: remote access terminates at FastAPI,
  and FastAPI is the only thing that talks to MQTT. A broker reachable from
  the internet is a gate opener with no auth policy in front of it
- `allow_anonymous false`, per-client credentials. The broker can open a gate,
  so an unauthenticated broker is an unlocked gate
- Credentials come from environment variables on the server side and
  `secrets.h` on the firmware side. Never in a committed config file
- Distinct, stable client IDs (`gate-esp32`, `gate-api`). Duplicate IDs cause
  a silent reconnect loop as each client kicks the other off

## Topics

| Topic | Direction | Retained | QoS | Purpose |
|---|---|---|---|---|
| `gate/availability` | ESP32 to broker | yes | 1 | LWT: `online` / `offline` |
| `gate/state` | ESP32 to broker | yes | 1 | Current gate state |
| `gate/cmd/trigger` | API to ESP32 | **no** | 1 | Pulse TRG-COM |
| `gate/cmd/ack` | ESP32 to broker | no | 1 | Command outcome |

### Retained flags are not stylistic

- `gate/state` **is** retained, so the app gets the real state the instant it
  subscribes instead of a blank screen until the next publish
- `gate/cmd/trigger` is **never** retained. A retained command is redelivered
  to the ESP32 on every reconnect, which means the gate opens by itself after
  a power cut. This is the single most dangerous mistake available here
- `gate/availability` is retained and set as the Last Will, so the app shows
  "controller offline" rather than a stale "closed" when the ESP32 drops

## Payloads

JSON, always an object, always carrying a schema version so an old app talking
to new firmware fails loudly instead of guessing.

```jsonc
// gate/state (retained)
{ "v": 1, "state": "closed", "rssi": -67, "uptime_s": 84120, "ts": 1753036800 }

// gate/cmd/trigger
{ "v": 1, "request_id": "5f3c...", "source": "app", "ts": 1753036800 }

// gate/cmd/ack
{ "v": 1, "request_id": "5f3c...", "result": "accepted", "ts": 1753036801 }
```

- `gate/availability` is the one exception: a bare `online` / `offline` string,
  because it is set as an LWT and simpler is more robust there
- Reject unknown `v` values rather than best-effort parsing them

## Gate State Enum

Defined once here and mirrored in all three codebases:

`unknown` | `open` | `opening` | `closed` | `closing` | `stopped` | `fault`

- `unknown` is the honest startup value before the status LED has been
  decoded. Never default to `closed`: showing a closed gate that is actually
  open is the worst possible lie this system can tell
- `stopped` is a partially open gate halted mid-travel, which the D3 reaches
  when triggered during motion
- `fault` covers an undecodable or contradictory LED pattern

## Command Idempotency

- Every command carries a unique `request_id` generated by the API
- QoS 1 guarantees at-least-once delivery, so **duplicates will happen**. The
  ESP32 keeps a short history of recently seen `request_id`s and ignores
  repeats
- This matters more here than in a normal system: the actuator is a physical
  gate, and a duplicate delivery means a second pulse, which on the D3 means
  stop or reverse rather than a harmless no-op
- The API never retries a command silently. A retry is a new `request_id`, and
  only after an ack times out

## Keepalive

- MQTT keepalive of 30s, so a dead ESP32 is detected in well under a minute
  and the LWT fires while the information is still useful
- The ESP32 republishes `gate/state` on every change, plus a heartbeat
  republish at a fixed interval so a missed message self-corrects
